hal-deploy-run behavior (worked out empirically, binary is stripped/no --help):
  - Running it with path arguments (e.g. `hal-deploy-run /bin/id`, `hal-deploy-run
    /usr/bin/touch /tmp/x`, `hal-deploy-run /path/to/script.sh`) produces ZERO
    observable effect: no output, no created files, exit code 0. argv is NOT
    used as "the command to run".
  - Confirmed via a python3/ctypes ptrace syscall tracer (strace/ltrace not
    installed on box) that it does: getpwnam("builder") -> setresgid(1001) ->
    setresuid(1001) -> then execs a shell. (Tracing itself strips the file
    capability grant since the tracer is unprivileged, so setuid/setgid
    EPERM'd under trace -- but this confirmed the uid/gid target is 1001 and
    the call order.)
  - The real mechanism: it drops privileges to builder (uid=gid=1001) and then
    runs bash READING FROM STDIN. It's a "pipe a script in, it runs as
    builder" tool, not an argv-based launcher.
  - Gotcha: `su deploy -c '...'` consumes exactly one line of the piped stdin
    for su's own password prompt; everything piped in AFTER that first line
    passes through to whatever su ultimately execs, including hal-deploy-run's
    inherited stdin. So the working invocation pipes password + script as one
    stream.
