    #!/bin/sh
    if [ "$(id -un)" != "releng" ]; then
      echo "halcyon-runas-releng: refusing to run as $(id -un); this helper only runs as releng" >&2
      exit 1
    fi
    # Invoked by pkexec (as releng, once com.halcyon.runas-releng is
    # authorized -- see /etc/polkit-1/localauthority/50-local.d/49-halcyon-runas.pkla
    # and the self-guard above, which is what actually pins the target to
    # releng; the .pkla grant alone cannot see pkexec's --user choice). Args
    # optional: with args, exec them; with none, drop into an interactive shell.
    if [ "$#" -gt 0 ]; then
        exec "$@"
    else
        exec /bin/bash -i
    fi

  -> this comment is the whole vulnerability, spelled out by whoever wrote
  it: there's a legacy-style .pkla grant at
  /etc/polkit-1/localauthority/50-local.d/49-halcyon-runas.pkla that
  authorizes the com.halcyon.runas-releng ACTION for svc-deploy (or its
  group) with no password (Result=yes / equivalent). But a .pkla/.rules
  grant on an action is not parameterized by pkexec's --user target -- it
  authorizes "may invoke this action," not "may invoke it as exactly uid
  1002." The developer's OWN comment admits this ("the .pkla grant alone
  cannot see pkexec's --user choice") and patches around it with the
  in-script `id -un != releng` guard -- meaning the *policy* grants svc-deploy
  the right to pkexec this binary as ANY --user (root included), and the only
  thing stopping that from being a full root escalation is the script's own
  userland self-check, which happens to align with the intended scope here.
  This is exactly kael's line: "a policy always says more than the person
  who wrote it meant it to" -- the .pkla says more (any --user) than the
  authors meant (releng only), and only an unrelated shell-script guard
  narrows it back down. For this level the guard's scope (releng) is exactly
  the objective, so no need to fight it further -- just call it correctly.

gotchas:
  - writing job output into a HOME directory owned by a different account
    than the job's post-setresuid euid fails (Permission denied) even
    though the process is now that higher uid, because gid never changed --
    write to /tmp instead (see recon section above). Same underlying lesson
    as level4/5's "leftover files," just hitting it from the write side
    this time instead of the cleanup side.
  - getcap -r / on this box is extremely noisy (spams "Failed to get
    capabilities" for hundreds of /sys/kernel/** virtual files under a
    non-root, non-capability-bearing uid) -- not a useful recon step here
    unlike on the ghost2 box; ignore it and go straight for
    pkaction/polkit instead once kael's fragment points at "policy."
  - default pkexec target is root, not the program's "natural" account --
    `pkexec /usr/local/sbin/halcyon-runas-releng` (no --user) runs it AS
    ROOT, which immediately trips the script's own `id -un != releng` guard
    and exits 1. Must pass `--user releng` explicitly to land in the
    intended (and actually-authorized-without-password) path.
  - outer ssh to 204.168.229.209 threw the same benign
    "client_global_hostkeys_prove_confirm: server gave bad signature"
    noise on every connection (known quirk, harmless, ignore).
