  plaintext only exists while the unit is up, gone the moment it stops.)

  cat /opt/halcyon/signer-daemon.sh (root:root 755, but this is the key

    shopt -s nullglob

gotchas:
  - file ownership inside a payload matters based on WHO DOES THE
    REDIRECTION, not who ran the innermost command. A payload shape like:
      { pkexec --user releng ... 'cmd producing output'; } > /tmp/out.txt
    runs cmd as releng but the shell doing `> /tmp/out.txt` is still
    svc-deploy (the account deploy-step.sh actually executes as) -- so the
    resulting file is svc-deploy-owned, and a LATER cleanup attempt that
    tries `pkexec --user releng ... rm -f /tmp/out.txt` fails with
    "Operation not permitted" (releng isn't the owner, /tmp has the sticky
    bit). Fix: rm files with whichever account actually owns them, which
    for anything created via plain `>` redirection in these payloads is
    always the outer account (svc-deploy here), not whatever pkexec'd
    identity produced the piped-through content.
  - signer-owned artifacts (anything a signer-plugins.d plugin itself
    writes with `cp`/`chmod`, not via outer redirection) can only be
    cleaned up by running ANOTHER plugin through the same signer-reload
    cycle -- neither svc-deploy nor releng can touch them directly. Budget
    an extra reload round-trip for cleanup whenever the exploit plugin
    leaves files behind under its own uid.
  - the credential handoff on this box is NOT systemd's LoadCredential=
    directive (no such line in the unit) -- it's a hand-rolled equivalent
    via `ExecStartPre=+... install -m 0400 -o signer ...` copying
    /etc/halcyon/signing.enc into RuntimeDirectory=. Same lifecycle
    property (root-owned source, non-root-readable copy that only exists
    while the service is up, wiped when RuntimeDirectory is torn down on
    stop), just implemented directly instead of via the systemd feature --
    worth checking `systemctl cat` for the ACTUAL mechanism rather than
    assuming a specific systemd directive name from the objective brief.
  - outer ssh to 204.168.229.209 threw the same "channel 0: open failed:
    connect failed: ssh: unexpected packet in response to channel open"
    flakiness as promised -- needed 3-4 retries on the very first
    connection test and on the initial deploy/builder/ops chain run before
    one went through; every subsequent pipeline-side command over the
    already-negotiated ProxyCommand path was reliable. Same benign
    "client_global_hostkeys_prove_confirm: server gave bad signature"
    noise on every successful connection as prior levels, harmless.
  - before starting, checked `ps aux` for stray claude native-binary
